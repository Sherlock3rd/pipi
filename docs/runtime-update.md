## 已确认的请求含义

标准请求：**下拉更新最新的小皮**。

该请求只更新当前设备的小皮运行包：识别操作系统和芯片，选择对应包，自动退出正在运行的旧版，替换后自动启动新版，并清理旧版程序包。这里将用户所说的“允许包文件”按上下文解释为“运行包文件”。

不执行源码仓库全量拉取、克隆或清理，不下载原始视频、照片、制作资料、SDK和测试输出。运行包包含程序、必要运行时、资源与许可证，不能只换 EXE。仅当用户明确提出源码开发或重新构建时，才进入开发工作流。

用户追加确认：每次阶段性开发完成后，必须打包并上传完整运行包，方便其他设备更新。采用同一 GitHub 仓库 `Sherlock3rd/pipi` 的 Releases 附件分发，源码提交继续排除构建包；“上传到git”在发行场景指上传该仓库的正式发布附件，不把大包提交进 Git 历史。

“最新”指最新通过验证的正式发布版。若 main 已有更新但尚未形成正式包，接收设备保留当前版本并说明；这不免除开发侧完成阶段性打包上传的义务。未发布运行包的阶段只能报告“代码完成、发行未完成”，不能宣称交付完成。

## 设备与安装定位

| 目标设备 | 运行包 | 当前边界 |
| --- | --- | --- |
| Windows x64 | `Chenpi-win-x64.zip` | WPF，自包含运行时；系统最低版本应写入发行清单 |
| macOS / Apple 芯片 | `Chenpi-osx-arm64.zip` | 当前包要求 macOS 15+ |
| macOS / Intel | `Chenpi-osx-x64.zip` | 当前包要求 macOS 15+ |

检测实际安装目标设备的系统版本和硬件架构，不能用远程执行机的系统或 Rosetta 下的进程架构代替。当前构建脚本没有 Windows ARM64 包；遇到 Windows ARM64、32位系统或其他不支持平台时说明缺包，不擅自视为已验证兼容。

优先通过当前用户正在运行的程序绝对路径、已登记的安装位置及快捷方式定位。同一设备有多个安装且无法唯一定位时，列出具体路径询问目标。没有安装时说明这是首次安装，先确定安装目录。不能全盘匹配名字后覆盖或删除。

## 完整更新流程

以下为落实已确认要求的执行约束；实现时不得扩大运行包更新范围。

1. **锁定更新目标。** 对安装目录加更新锁，记录旧版标识、进程路径、实际存档目录、自启状态及启动入口。重复请求复用本次事务，不同时替换。拒绝静默降级；已是目标版本时报告无更新，未运行则按请求启动，已运行不额外重启。
2. **确定版本。** 选择最新通过验证的正式发布版，排除草稿、预发布和失败构建。发现最新版后固定其版本、提交与资产ID，下载与校验均使用同一发布快照，避免更新期间 latest 变化而混包。某平台缺包时说明并保留旧版。
3. **下载到暂存目录。** 旧版此时继续运行。预检目录写权限、系统兼容性，以及下载、解压、旧版保留、存档备份所需空间。网络中断可重试；下载未完成或校验失败不得关闭旧版。
4. **验证完整新包。** 从指定仓库的可信发布清单取得大小和 SHA256，核对 ZIP、入口、资源清单及架构；哈希用于一致性，不能代替发布者身份验证。解压路径必须位于暂存目录，拒绝路径穿越、外指符号链接和重解析点。Mac 保留可执行权限并验证应用签名，不改写已签名 `.app` 内容。
5. **保存并退出旧版。** 自动校验并保存有效的未保存设置，再调用应用真正的退出/保存流程，等待存档写入完成及目标进程退出。无效草稿保留并提示处理，不擅自修正或丢弃。关闭窗口不算退出；仅操作当前用户、对应安装路径的进程，不按 `dotnet` 或模糊名称批量杀进程。确认卡死/退出超时后，先备份已落盘数据并验证可读，再强制关闭本次目标进程；备份失败则停止替换。强制关闭后确认进程退出，再取最终稳定数据副本用于恢复。自动保存不隐含重排照料期限或更改有效设置。
6. **备份与完整替换。** 停止写入后备份实际存档和行为配置，验证备份可读；把旧程序暂存于已登记的回滚目录。暂存新目录与目标保持同卷，采用整包目录切换并记录恢复步骤，不在旧目录上零散覆盖。Windows DLL锁、杀毒软件占用、Mac目录权限或中途断电须可恢复。若安装目录混有源码或自定义文件，先隔离明确归属的运行包，不能整目录删除。
7. **自动启动和验收。** 从固定安装路径以原用户身份启动一次，保留实际数据目录及正式运行所需参数。核对新进程路径、版本、资源成功加载、存档可读与持续渲染/心跳；不能把旧进程、启动器退出码或单实例拦截当成新版启动成功。沿用现有每次新进程一次的开场规则。全屏避让或隐藏状态不等于启动失败，需结合内部状态判断。
8. **成功后清理。** 只有新版健康检查通过才清理已登记的旧程序目录、旧安装ZIP及本次临时文件。失败则保留旧版并恢复启动；不能先删除旧包。仅清理能证明属于本安装的旧产物，不扫描删除整个 Downloads、dist、项目根目录或所有名为 Chenpi 的目录。存档及其备份不属于旧包。清理失败应报告“新版已启动，旧包清理未完成”，不能重复安装或声称全流程成功。
9. **给出结果。** 报告设备/架构、旧版到新版、源码提交、安装路径、启动验证、存档保留与旧包清理结果；失败说明停在哪一步、是否回滚及剩余手动操作。写入本地更新日志，便于下次识别与断点恢复。

健康检查的信号和超时时间须在实现阶段结合冷启动、完整开场及隐藏模式验证，不能仅固定等待几秒即删除旧包。切换前写入事务记录，每次重试先恢复未完成事务。

## 存档与启动入口

Windows 默认数据目录为 `%LOCALAPPDATA%/Chenpi`，macOS 为 `~/Library/Application Support/Chenpi`。若以 `--data-dir` 指定其他位置，使用实际路径。保护 `pet-state.json`、其备份、`behavior-settings.json`、家具位置、陪伴时间、照料状态和期限、缩放、音量、静音、悬浮及自启设置。

更新在当前设备继续使用本地存档，不隐含跨设备存档同步。备份在正常退出并确认落盘后生成。若新版会迁移存档格式，发布清单须声明迁移与回滚兼容性；必要时回滚程序和更新前的配套存档，同时保留新版失败期间的数据副本，避免旧版读取不兼容数据或无提示丢失进度。

保持固定安装入口与已有快捷方式。自启原来关闭就保持关闭；原来开启则确保仍指向固定新入口。更新临时阻止旧进程重启的机制必须在完成、取消及失败时恢复原状态。不能让更新工具在待替换目录内运行。

## 阶段性发布要求与能力缺口

每次阶段性开发完成后，开发侧必须完成以下交付，接收更新的设备不承担构建责任：

1. 从固定源码提交构建完整 Windows x64、macOS Apple芯片及Intel运行包，包含必要运行时、全部运行资源与许可证；不以源码ZIP、单个EXE或需要旧包拼装的差量替代完整包。
2. 按平台完成对应构建、资源一致性和启动/运行验收；编译通过不等于原生桌面交互通过。某平台未通过时保留上一个正式版，报告未完成平台和原因。
3. 将三种包、校验文件、发行清单及版本说明上传至指定仓库的同一草稿Release。全部上传和验收通过后再公开为正式版，避免客户端发现半成品；下载地址必须绑定具体版本。
4. 从远端回读资产列表、大小、版本及SHA256，并下载回验正式附件；确认其与本地验收包一致且目标用户可访问，之后才报告阶段性交付完成。仅Actions临时产物、只有本地dist或提交源码均不算完成。
5. 三种平台使用统一发行版本和源码提交。仅某个平台代码变化时，仍须提供整套对应发行包；若复用未变包，须有可审计的运行输入完全一致证据，明确原构建提交及复用来源，不伪造包内构建标识。

本次规则文档变更不冒称新的程序功能版本，也不为了记录规范重复发布未变化的运行包。后续功能、修复及资源优化阶段须执行上述交付。

## 已确认策略与异常边界

用户已选择最新正式版，并追加阶段性开发完成必须打包上传；已选择自动保存有效设置再退出、卡死时先备份存档再强制关闭。这些操作在之后标准更新请求中无需重复询问。

卡死时可能无法取得未保存的内存草稿，备份不能恢复从未落盘的数据；须在结果中说明。仅在目标安装不唯一、无效设置、首次安装位置未定、系统权限/安全批准或存档无法安全恢复等实际阻碍下请求用户处理。
