# PROTOTYPE-025：资源优化须同时核对像素、持有关系与播放时序

2026-10-08，macOS 适配与资源优化。

## 问题

全量解码动画导致工作集约 4.69 GB。仅将帧列表改为 LRU 还不够：普通字典保存图像边界时仍会强引用淘汰帧，后台解码若在缓存锁内执行，会阻塞已缓存帧的展示。只预读当前片段则会在转身、起身和照料接缝临时解码。

最初两个 GUI 预览与全量像素审计并行运行，性能样本相互干扰；不能据此判断正常运行的卡顿。Avalonia 固定 60 Hz 定时器与呈现节奏也存在错位，改为窗口动画帧回调。离屏首帧预热未改善本机测得的启动延迟，已撤销，不能把增加的初始化工作包装为收益。

## 修复与验收

- 缓存按实际解码字节预算，元数据用弱引用；解码在缓存锁外执行，单预读队列避免积压。
- 保留全部帧、原清单引用与时长，独立播放状态快照预读 0.6 秒，回归测试确认预测不改变真实状态。
- 无损 WebP 开启透明 RGB 精确保留，每帧重新解码逐字节比较；另外比较 WPF 实际预乘、裁切和边界，15349 帧像素/边界差异均零。
- 单独运行 60 秒 Windows 预览，工作集约 311 MB，P95 帧间隔 17.56 ms。结果仅代表已测 Windows 场景，不能作为 Mac 内存或真实游戏/Retina 验收。

证据：`docs/qa/macos-resources/`。Mac 原生验证和发布结果记录在 `docs/macos-and-resources.md`。

## Mac 包签名追加

首轮两种架构均编译通过，但 `.app/Contents/MacOS` 散放托管 PE DLL 时，严格签名报 `code object is not signed at all`（子项 `System.Diagnostics.Contracts.dll`）。改为不裁剪的 single-file 程序集、数据放标准 Resources、原生库先签、应用最后签。禁止跳过签名校验来声称包可用；增加压缩前的快速 Mac 原生启动测试，避免每次等待全量压缩后才发现宿主问题。

## 参数面板追加

Avalonia 文本事件与 WPF 的同步时机不同；仅依赖 `TextChanged` 更新草稿，程序夹具连续设值后立即保存会读到旧值。保存、导出、切换节点与关闭前直接读取当前控件，并忽略已被替换控件的延迟事件。夹具实际验证保存回读、非法值拒绝、照料期限重排及默认草稿隔离；不以共享模型测试替代宿主 UI 测试。
